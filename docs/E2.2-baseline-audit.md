## What the inspection actually found — and where it contradicts the prediction

The predicted baseline expected `Colour ✕` and `Typography ✕` across all five.
**Both predictions are wrong**, and in a way that matters for the work:

**Colour is mostly already compliant.** Three of five rooms contain *zero* hex
literals. Only two carry any, and every value is already canonical:

| Room | Hex literals |
|---|---|
| BuildBoard | none |
| ProductionLine | none |
| ImpactDashboard | none |
| InspectionHangar | `#0A7F73` `#1a7a4a` `#3a4a5a` `#F5A623` |
| DemoStudio | `#0A7F73` `#0D0D0F` `#1a7a4a` `#3a4a5a` |

Both offenders already import `T` from `../os/forge.js`. So this is eight
literal→token substitutions, not a colour system problem. The earlier count of
"6 and 5 hexes" was *occurrences*; the distinct values are 4 and 4.

**Typography is `⊖`, not `✕`.** No room in the five declares any
`font-family` at all — zero matches across all five files. They inherit type
from `Room` and the global stylesheet. There is nothing to convert. Marking
these `✕` would invent work; the correct reading is that the dimension does not
apply until a room sets type itself.

**Identity is `~`, not `✕`.** All five already use the `Room` kernel wrapper,
which supplies room identity from the `ROOMS` registry — id, name, sequence,
camera. They do not use `RoomShell`, which additionally renders the kicker,
Poppins Black title and principle. So identity exists but is the *older* kernel
wrapper. This is a real distinction: these rooms are not unwrapped, they are
wrapped by the wrong generation of primitive.

## Per-dimension findings

**Projection.** Verified by destructure, not assumption:

| Room | Source |
|---|---|
| ProductionLine | `const { machineStates } = useForgeActivity()` — ✓ shared |
| ImpactDashboard | `const { log } = useForgeActivity()` — ✓ shared |
| DemoStudio | `const { event, log, hubStates, machineStates, publish } = useForgeActivity()` — ✓ shared |
| InspectionHangar | imports `buildRuntime` but **never calls it** — ⊖ |
| BuildBoard | no data source — ⊖ |

The Chief Architect's concern that `buildRuntime` might be called with local
event data is **not borne out**. `DemoStudio` calls
`buildRuntime({ event, log, hubStates, machineStates })` with values destructured
from `useForgeActivity()` — the shared stream. `InspectionHangar` imports it and
never invokes it: a dead import, not a projection violation.

**State.** `ProductionLine` displays `"active"`; `DemoStudio` displays
`"active"`/`"idle"`. Both are canonical. No non-canonical state strings found in
any of the five.

**Feed.** Only `DemoStudio` renders events (`.map` over a log-derived list) — the
single `✕` on this dimension and the architectural correction the sprint calls
for. The other four render no feed: `⊖`, correctly.

**Causation.** No room displays consequences. All `⊖`.

**Contract.** No room has a JSDoc block or a `CONTRACT` export. All `✕`. This is
the dimension with genuinely five failures.

**Not verified by inspection:** whether `ProductionLine`'s machine grid and
`InspectionHangar`'s scan behaviour survive a `RoomShell` wrap. That requires
running them, which the audit cannot establish from source.

## API corrections for the convergence session

The instructions reference an API that does not exist in this repo. Writing code
against it would fail:

| Instruction says | Actual |
|---|---|
| `src/kernel/design/tokens.js` | `src/os/forge.js` |
| `T.color.teal`, `T.color.pink` | `T.teal`, `T.pink` |
| `T.font.mono`, `T.font.sans` | `FONT.mono`, `FONT.ui`, `FONT.display` |
| `T.text.*` type scale | no scale exists; sizes are literals, `S` is spacing |
| `useCausalProjection()` | `project(log, MISSIONS)` returns `.consequences` |
| `demoStory.js` | `src/os/story.js` — `MANUFACTURING_STORY`, `STORY_META` |
| principle registry as a new file | `PRINCIPLES` in `src/os/forge.js`, keyed by room id |

`PRINCIPLES` **already contains all five room ids** — `build-board`,
`production-line`, `impact-dashboard`, `inspection-hangar`, `demo-studio`. The
principles are written and registered; they are simply not *displayed*, because
these rooms use `Room` rather than `RoomShell`. So Principle is one wrapper
change per room, not a registry addition.

## Recommended sequence

Unchanged from the directive, and the ordering holds: BuildBoard (17 lines,
proves the RoomShell swap), ProductionLine (28), ImpactDashboard (42),
InspectionHangar (71, plus 4 tokens and a dead import), DemoStudio (210, the
feed correction) last.

**Open question for the architect:** `Room` supplies identity from the registry
and mounts the camera contract. `RoomShell` supplies the kicker, Poppins Black
title and principle. Should converged rooms use `RoomShell` *inside* `Room` —
keeping the camera contract while gaining the principle header — or replace
`Room` entirely and lose the camera binding? The five rooms all declare a
`camera` in the `ROOMS` registry, so replacing `Room` outright may drop
behaviour. This needs deciding before BuildBoard is touched.
